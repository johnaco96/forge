# Forge v1.1.0 release notes

Status: **LOCAL RELEASE CANDIDATE READY** for supervised production under the
documented RC4 human waiver. GitHub CI/CD and publication remain
user-controlled external gates. **AUTONOMOUS PRODUCTION: NOT AUTHORIZED.**

## Changes since v1.0.1

Forge 1.1.0 adds the production-hardening layer around the implemented Phase
0–8 control plane:

- fail-closed Docker-compatible OCI containment with a read-only root, private
  HOME/tmp, bounded mounts, no Linux capabilities, no-new-privileges, resource
  limits, disk preflight/watchdog, Docker `--init`, and bounded
  signal/descendant cleanup;
- per-invocation provider credential selection, short-secret redaction,
  credential-free evaluators, explicit evaluator executable/version
  prerequisites, fail-closed preflight, and typed infrastructure failures;
- candidate credential-value scans across tracked, untracked, ignored, binary,
  symlink, path-name, and chunk-boundary evidence before staging or durable
  capture, with forced workspace destruction on contamination;
- centralized workspace disposition for PASS, failure, no-change, timeout,
  cancellation, contamination, and cleanup failure, with durable disposition
  events after evidence capture;
- process-group termination for normal completion, timeout, cancellation, and
  descendant cleanup; cancellation stops later evaluation steps and cannot be
  converted to PASS;
- hardened Git worktree creation, branch/path validation, linked-worktree
  metadata checks, disabled hooks/external diff/textconv, neutralized candidate
  clean filters, and removal of hostile Git environment overrides;
- WAL-safe SQLite backup, no-clobber publication, staged verified restore,
  sidecar process locking, migration gates, and a rehearsed versioned rollback
  unit;
- stronger execution provenance/configuration fingerprints, exact router
  replay, recommendation-only routing, and preserved human authority;
- deterministic native packaging/checksums plus CI, security, and release
  workflows; and
- `forge doctor --live-agent-probe`, which uses a disposable Git workspace and
  requires a selected real provider to create exactly one controlled marker.

## Provider and containment remediation

RC3 exposed that Codex 0.147.0 attempted a nested Bubblewrap namespace inside
Forge's already constrained OCI container. The outer boundary intentionally
lacks `CAP_SYS_ADMIN` and privileged namespace access, so Bubblewrap could not
start. RC4 does not grant those privileges. In required containment, Forge
invokes Codex's externally-contained mode and treats the existing OCI container
as the sole security boundary. Native/development Codex retains its configured
workspace sandbox and approval policy.

Production-contained agents require image-provided `claude-forge` and
`codex-forge` wrappers. Claude runs bare with a private one-shot API-key helper;
Codex logs in only within the disposable HOME. Both remove the credential
environment before model-directed tool execution. Evaluators request no
provider credential and run as separate contained commands.

Both exact-image controlled-mutation probes passed. Claude and Codex
authenticated, performed the required disposable mutation, left the Forge
source checkout unchanged, and retained no credential. Codex reported
`inner sandbox=bypassed, boundary=Forge OCI`, directly confirming that the RC3
nested-sandbox failure is resolved under RC4.

## Operations and rollback

The backup path is WAL-safe and verified; restore is staged, locked, and
rollback-safe; cleanup decisions are durable; failed workspaces follow the
configured retention policy; provider streams have a separate retention
window; disk preflight/watchdog failures remain typed infrastructure evidence;
and Docker control calls plus child process groups are bounded.

Rollback to v1.0.1 is a three-part deployment unit: the previous binary, its
matching strict configuration, and a verified database snapshot. The rehearsal
proved that v1.0.1 can read the version-matched schema-12 backup without
mutating it. Never reverse migrations in place or pair an old binary with a new
strict config.

## Known limitations and external gates

- The RC4 profiles use `network=allowed` for provider APIs and dependency
  installation. Forge does not provide destination-level egress allowlisting;
  supervised deployment operators must enforce or accept that policy outside
  Forge.
- This does not expose the Docker socket, host home, primary worktree,
  arbitrary host mounts, privileged mode, or broad Linux capabilities.
- The frozen nine-outcome gate is not fully satisfied because two tasks are
  human-waived.
- No Git remote is configured and GitHub CI/CD has not run. Workflow definitions
  are not remote execution evidence.
- Routing remains recommendation/shadow-only at the unchanged `0.05` margin;
  the prospective holdout has not been consumed.
- Automatic routing, merge, policy promotion, and team dispatch remain
  disabled.
- Native local qualification covers Darwin ARM64; the OCI runtime covers Linux
  ARM64. GitHub workflows build macOS ARM64 and Linux x86-64 artifacts only when
  the user runs them.
- Pushing, remote CI, the GitHub release, and all package/container publication
  remain user-controlled actions.
